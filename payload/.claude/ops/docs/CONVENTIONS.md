# 에이전트 작업 규약 — L1 · L2

이 파일은 **모든 에이전트**(구현자·검증자·탐색자)가 지키는 것만 담는다. 세션을 지휘하는 쪽의 규약(L3 —
브리프·검증 배치·모델 고르기·사용량 한도)은 `.claude/skills/ops-orchestrator/SKILL.md` 에 따로 있다 —
작업 에이전트는 읽지 않아도 된다.

이 파일은 템플릿(`claude-ops`)의 **관리 파일**이다. 소비자 저장소에서 직접 고치면 `claude-ops check` 가
실패한다 — 고치는 곳은 템플릿 한 곳이다. 프로젝트별 값은 `.claude/project.env`, 프로젝트 지식은
`CLAUDE.md`(둘 다 오버레이 — 템플릿이 덮지 않는다).

각 항목의 **"왜" 사고 사례는 일반화한 문장**이다 — 실제 사고는 항상 어느 한 프로젝트에서 일어났지만,
같은 모양의 사고가 프로젝트를 가리지 않고 반복됐다. 서비스 고유의 사례를 보태고 싶으면 그 서비스의
CLAUDE.md 나 `.claude/rules/` 에 적는다(이 파일은 공통부라 서비스 이야기를 넣지 않는다).

## 설계 원칙

> **규약은 불변식을 고정하고, 해법은 고정하지 않는다.**
> **모든 요구에는 거부권이 있다 — 안 했으면 보고서에 이유를 적으면 된다.**

이 규약이 막으려는 것은 나쁜 판단이 아니라 **침묵하는 누락**이다. 요구를 지키지 않는 것은
허용되고, 지키지 않았다는 사실을 감추는 것만 허용되지 않는다. 그래야 규약이 틀렸을 때
드러나고, 판단이 필요한 곳에서 판단이 살아 있다.

그래서 어떤 항목도 "이렇게 구현하라"고 말하지 않는다. "이것이 보장되는가"만 묻는다.

# L1 · 기계가 검사한다

판단이 필요 없는 것들이다. 스크립트가 걸러내므로 외울 필요가 없다. **스크립트는 읽지 말고 실행만 한다**
(근거 주석이 길어 읽으면 컨텍스트만 찬다).

**작업을 시작하기 전에 반드시 실행한다.**

```bash
bash .claude/ops/bin/preflight.sh
```

검사하는 것:

| 검사 | 왜 |
|---|---|
| 전체 refspec 으로 fetch 후 현재 브랜치가 최신 기본 브랜치를 조상으로 갖는지 | 오래된 기준점에서 갈라져 나오면 머지할 때 남의 작업을 되돌린다. 얕은 클론에서 `git fetch origin <브랜치명>` 만 하면 원격추적 ref 가 갱신되지 않아 이 사고가 조용히 일어난다. 실제로 낡은 기준점의 브랜치를 그대로 머지했으면 이름 바꾸기 작업 전체와 릴리즈 정리 워크플로가 되돌아갈 뻔했다 |
| 작업 트리가 깨끗한지 | 남의 변경 위에 쌓지 않기 위해 |
| 커밋 트레일러 문자열 출력 | 트레일러는 **판단하지 말고 출력된 것을 그대로 복사**한다. 직접 지어내면 틀린다. 공동 작성자 줄은 **그 작업을 한 모델**을 적는다 — 오케스트레이터가 `CLAUDE_COAUTHOR` 로 넘기고, 넘기지 않으면 project.env 의 기본값이다(L3-12). 넘긴 값의 모양이 틀리면 시작하지 않는다 |

**작업을 끝낸 뒤에 반드시 실행한다.**

```bash
bash .claude/ops/bin/postflight.sh
```

검사하는 것: 보고서 파일 존재, 보고서 맨 앞 `## 요약` 이 20줄 이내인지, 보고서에 L2 답이 모두 있는지,
커밋 트레일러가 맞는지, 작업 트리가 깨끗한지, 보호 경로를 고치지 않았는지. 그리고 템플릿에서 온
관리 파일이 그대로인지(`claude-ops check` — 아래 "관리 파일" 참고).

**postflight 의 기준점은 항상 `origin/<기본 브랜치>` 이고 선언으로 바꿀 수 없다.**
한때 `BASE_REF` 환경변수로 선언할 수 있었으나 없앴다 — 기준점을 넉넉히 잡으면 검사
대상이 줄어 게이트를 **조용히** 우회할 수 있었고, 정작
그것이 없애려던 머지 커밋 오탐도 없애지 못했다(후보 3개를 다 넣어도 그대로 실패).
오탐의 원인은 기준점이 아니라 둘이었고, 각각 다르게 고쳤다.

- **남의 커밋이 "트레일러 없는 커밋" 으로 잡히던 것** — 머지 커밋은 반대쪽 부모의
  이력을 전부 검사 대상에 넣기 때문이다. 검사 범위를 줄이는 대신, 트레일러가 없는
  커밋에 대해서만 **그 패치가 이미 기준 브랜치에 있는지**를 보고 건별로 면제한다.
  범위를 `--first-parent` 로 좁히는 방법은 쓰지 않았다 — 자기 커밋을 옆 브랜치에
  쌓아 머지하는 것만으로 검사를 통째로 피할 수 있게 된다.
- **기본 브랜치가 고친 보호 경로가 "이 브랜치가 고쳤다" 로 잡히던 것** — 두 점
  diff 는 두 트리의 차이라 브랜치가 기준의 자손이 아니면 방향이 뒤집힌다. 세 점
  diff(merge-base 기준)로 본다. merge-base 는 그래프에서 계산되므로 환경변수로
  옮길 수 없다.

**거부권은 범위가 아니라 항목 단위로 행사한다.** 트레일러가 없는 커밋이나 보호 경로
변경을 그대로 통과시켜야 한다면 `ACCEPT_UNTRAILERED=<sha>` ·
`ACCEPT_PROTECTED=<경로>` 로 **하나씩 이름을 적고, 같은 문자열을 보고서에도 적는다**
— 보고서에 없으면 통과하지 않는다. 기준점을 옮기는 것과 다른 점은 **무엇을 면제했는지가
유한하게 남는다**는 것이다. 면제된 항목은 언제나 출력에 나열된다.

### 관리 파일 (템플릿에서 온 것)

`.claude/ops/**` · `.claude/agents/ops-*` · `.claude/skills/ops-*` 와 생성물 `.claude/settings.json` 은
템플릿이 소유한다. 소비자 저장소에서 고치면 postflight 와 CI 가 실패한다.

- 고칠 것이 있으면 **템플릿에서** 고치고, 소비자는 `node .claude/ops/bin/claude-ops.js sync --ref <버전>` 으로 받는다.
- 서비스만의 설정(권한 규칙 등)은 `.claude/settings.overlay.json` 을 고치고 `node .claude/ops/bin/claude-ops.js settings`.
- **급하게** 소비자에서만 고쳐야 하면 `.claude/ops.lock` 의 `overrides` 에 `{"path": "…", "reason": "…"}` 를 적는다.
  사유가 없으면 받지 않고, 있는 동안 check 가 경고로 계속 알린다 — 거부권과 같은 원리(안 했으면 이유를 적는다).

### 출력은 파일로, 요약만 화면에

테스트·빌드처럼 출력이 긴 명령은 `bash .claude/ops/bin/run-quiet.sh --label <이름> -- <명령>` 으로 돌린다.
종료 코드는 그대로이고, 화면에는 요약과 실패 블록만, **전체 출력은 실행마다 고유한 로그 파일**에 남는다.
`명령 | grep … | head` 로 줄이지 않는다 — 파이프의 종료 코드는 마지막 명령의 것이라 실패가 초록이 된다.

# L2 · 보고서에 답이 있어야 한다

**방법은 자유다.** 아래 여섯 가지에 대한 답만 보고서에 있으면 된다.
`.claude/ops/templates/report.md` 를 복사해 쓴다. 맨 앞 `## 요약`(20줄 이내)은 읽는 쪽이 **그것만** 읽는다는
전제로 쓴다.

각 항목에서 **"해당 없음"** 과 **"안 했음 + 이유"** 는 정당한 답이다.
비워두는 것만 안 된다.

### 1. 진입점 전수

새 검사·제약·불변식을 넣었는가? 그렇다면 **그 효과에 도달하는 경로를 전부 세고**,
누락이 **실패로 드러나는** 장치를 뒀는가.

> 왜 — 치명적 결함 두 건이 정확히 이 모양이었다. 이중 청구 방어를 한 경로에만 걸어 다른 경로로
> 카드가 여러 번 긁혔고, 세션 무효화 검사를 한 곳에만 걸어 다른 곳이 우회했다. 둘 다 "검사를
> 넣었다"는 사실만으로는 못 막았다.
>
> 왜(두 번째 모양) — 「작업 중에는 로그인 금지」 를 화면(UI)에만 걸었다. 그 화면이 부르는 프로세스 간
> 통로(IPC 핸들러)는 조건 없이 동작해, 개발자 도구 콘솔에서 그 함수를 직접 부르면 금지된 순간에
> 로그인 창이 튀어나올 수 있었다. "진입점"이 UI 하나가 아니라 **그 UI가 부르는 통로까지**라는 걸
> 놓친 사례다.
>
> 잘 풀린 사례 — 검사 인자를 **필수 판별 유니온**으로 만들어, 빠뜨린 코드는 빌드가
> 안 되게 했다. 이건 하나의 해법일 뿐이고 다른 방법도 된다. 요구는 "빠뜨릴 수 없게
> 만들어라" 이지 "판별 유니온을 써라" 가 아니다.

### 2. 실제 경로를 타는 테스트

기능마다 **공개 진입점을 타는 테스트가 최소 하나** 있는가. 순수 함수만 검사하는
테스트로는 이 항목을 만족하지 못한다.

> 왜 — 상태 표시 테스트가 통과하고 있었는데 실제 배선이 끊겨 있었다. 함수를
> 손으로 만든 입력으로 직접 불렀기 때문이다. 사용자에게 잘못된 화면이 나갔다.
>
> 왜(같은 모양, 다른 프로젝트) — 구독 상태 표시가 **온라인 검증에 막 성공했는데도** "오프라인 확인
> 필요"로 떴다. 캐시 조회 함수가 출처 표시를 항상 「캐시」 로 덮어써서, 실시간 검증 성공이 표시 계산까지
> 도달하지 못한 탓이었다. **그런데 단위 테스트는 통과하고 있었다** — 표시 계산 함수를 손으로 만든
> 「실시간」 입력으로 직접 호출했기 때문이다. 실제 코드 경로(공개 상태 조회를 거치는)를 타는 통합
> 테스트로 바꾸고 나서야 잡혔다. 두 사고가 **거의 같은 모양**이라는 점 자체가, 이 항목이 프로젝트를
> 가리지 않는 진짜 위험이라는 근거다.
>
> "최소 하나" 다. 모든 것을 통합 테스트로 만들라는 뜻이 아니다.

### 3. 수치의 출처

주석·문서에 적은 숫자가 **테스트가 계산한 값**인가. 추론으로 적은 숫자가 있는가.

> 왜 — 재시도 횟수가 주석에 18회로 적혀 있었고, 검토자가 19회라고 지적했고,
> 실제로 시뮬레이션하니 15회였다. 세 번 틀렸다. 사람이 세면 틀린다.
>
> 반대 방향의 좋은 사례 — 앱 시작 시 권한 확인 지연 값(「1.5초 지연·4초 타임아웃」)을 추론이 아니라
> 페이지 로드 이벤트를 3조건×3회 계측해 정했다. 이 항목이 요구하는 방향과 같다.
>
> 계측 도구 자체도 틀릴 수 있다 — 토큰 집계 도구가 로그의 같은 응답 줄을 중복으로 더해 캐시 쓰기를
> 약 2배로 셌다(고유 메시지 id 로 세어 바로잡음). 숫자의 출처가 도구라면 그 도구가 무엇을 세는지도 확인한다.

### 4. 막히면 안 되는 것

검사·게이트·차단 장치를 추가했는가? 그렇다면 **무엇이 계속 가능해야 하는지 적고,
그 경로를 실제로 돌려봤는가.**

> 왜 — 릴리즈 전 설정 검사를 넣었더니 릴리즈 워크플로 자체가 멈췄다. "막아야
> 할 것"만 보고 "막히면 안 되는 것"을 안 봤다. 게이트는 항상 무언가를 같이 막는다.
>
> 왜(두 번째 모양) — 빌드 검사가 개발용 더미 키를 발견하면 빌드를 무조건 중단하도록 만들었더니,
> **실제 유료 키가 아직 없는 상태에서 낼 수 있었던 무료판 배포까지 막혔다.** 막아야 할 것은 "더미 키를
> 신뢰하는 빌드"이지 "유료 기능이 없는 빌드"가 아니었다. 의사를 환경변수로 밝히면 통과시키되 무엇을
> 포기했는지 크게 찍는 것으로 고쳤다. 같은 이유로 그 빌드 명령은 에이전트의 검증 명령(`VERIFY_CMD`)에
> 넣지 않았다 — 넣었으면 모든 에이전트가 여기서 막혔을 것이다.
>
> 왜(세 번째 모양) — 큰 파일을 읽지 못하게 하는 권한 규칙(`permissions.deny` 의 `Read(...)`)을 넣었더니,
> 그 경로를 **인자로 언급만 한** 자기 셸 명령(예: 그 파일 이름이 섞인 `grep`·`sed`)까지 막혔다.
> 읽기 차단 규칙은 도구 호출뿐 아니라 셸 명령의 인자에도 걸린다. 그 파일을 다뤄야 하면 경로를 직접
> 적지 않는 스크립트로 처리한다.

### 5. 공유 자원 변경의 사용처

타임아웃·커넥션 풀·전역 설정처럼 **여러 곳이 같이 쓰는 것**을 바꿨는가? 누가 같이
쓰는지 열거했는가.

> 왜 — 캐시 클라이언트에 명령 타임아웃을 걸면서 "부수적 이득"으로만 적었다.
> 그 값은 그 클라이언트를 쓰는 **모든 코드**에 걸린다. (이번에는 실제 영향이 없었지만
> 그건 확인해서 안 게 아니라 운이 좋았던 것이다.)
>
> 왜(두 번째 모양) — 화면 분할 계산처럼 **미리보기와 실제 출력 둘 다**가 같은 결과를 내야 하는 공용 계산을
> 고치면서 사용처 하나만 확인하고 다른 하나를 안 돌려보면, 미리보기와 실제로 나가는 화면이 어긋난다.
> 그런 파일은 보호 경로(L1)에 넣지 않는 것이 맞다 — 요구는 "고치지 마라"가 아니라 "고칠 때 두 사용처를
> 다 확인해라"이고, 그것은 기계 차단이 아니라 이 항목(보고서에서 사람이 확인)의 몫이다.

### 6. 미확인 목록

확인하지 못한 것을 **통과로 적지 않았는가.** 환경 제약으로 못 한 것, 대체 수단으로
확인한 것, 논리로만 확인한 것을 구분해 적었는가.

> 왜 — 가장 큰 위험은 실제 외부 서비스·실제 OS 에서 한 번도 안 돌려본 것이다. 그 사실이 보고서에
> 없으면 없는 위험이 된다.
>
> 왜(종류가 다른 두 번째 사례) — **패키징된 빌드에서만 드러나는 문제**가 있다. 새 모듈이 패키징 파일
> 목록에서 빠져, 개발 모드에서는 멀쩡한데 **설치본에서만** 모듈을 못 찾아 죽은 사고가 있었다. 에이전트
> 환경에서 대상 플랫폼의 설치본을 만들 수 없으면, 다른 플랫폼 타깃으로 패키징해 파일이 들어갔는지
> 확인하는 식으로 대체하거나 미확인으로 남긴다 — **이걸 새 L2 항목으로 만들지 않고 이 항목의 사례로
> 남겼다.** 이 환경에서 반복 검증할 수 없는 것을 항목으로 만들면 매번 "안 했음"만 적히는 죽은 항목이 된다.

## 일부러 넣지 않은 것

절제가 규약의 신뢰도를 만든다. 아래는 의도적으로 제외했다.

- **커버리지 수치 목표** — 숫자를 맞추려 의미 없는 테스트가 생긴다
- **TDD 강제** — 이 규약을 만든 프로젝트들의 실수 중 TDD 로 막혔을 것이 없다
- **아키텍처·코드 스타일 규칙** — 저장소에 이미 있다. 규약이 끼어들면 충돌한다
- **PR 본문 양식** — 지금 형태가 잘 작동한다
- **"패키징 빌드에서만 나는 문제" 전용 L2 항목** — L2-6(미확인 목록)의 사례로 충분하다
